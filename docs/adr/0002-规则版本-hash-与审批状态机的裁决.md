# 0002 · 规则版本 hash 与审批状态机的裁决

- **状态**：已裁决（2026-10-23，QT-42 X3a 实装时钉住）
- **场景**：规则要「可版本化、可审计、未审批不得生效」。落地前有三个必须一次说清的问题：
  ① `version_hash` 到底对哪些字段做内容寻址——若把 `description` / `status` / 时间也揉进去，改一句说明文案就会使快照失效、回测结果不可复现；
  ② 审批是几步——`draft → approved → active` 写成两次外部调用，还是一次动作内完成；
  ③ 定义行既要有「编辑头」又要表达「当前生效版本」，单指针无法同时表达这两件事，且会出现「新草稿把线上版本顶掉」的窗口。
- **决策**：
  1. **`version_hash` 只做语义寻址**：`sha256(域标签 + 长度前缀字段: rule_id / revision / scope / type / 规范化 params)`，域标签 `tellurion.risk_rule_version_hash.v1`。**不含** `description` / `status` / `created_at` / `approved_at`。`params` 先按 JSON 规范化（`json.Number` + 键序由编码器固定）再入 hash；规范化失败即拒收（fail-closed）。
  2. **`approve` 一次动作走完 `draft → approved → active`**：对外只有一个端点 `POST /api/risk/rules/{id}/approve`，响应 `status="active"`。同一规则有新版本被激活时，旧的 `active` 自动转 `deprecated` 并留一条 `deprecate` 审计；撤回不是删除，旧版本行永在。
  3. **`rule_defs` 双指针**：`head_revision`（编辑头，永远指向最大 revision）+ `active_revision`（生效版本，可为 NULL）。定义级 `status` 只表达「有没有生效 revision」（`active` / `draft`），**head 自身的状态由 revision 行表达**（列表视图的 `status` 取 head 行）。
- **理由**：
  - hash 只覆盖语义，才能满足「改文案不破快照、改规则必换 hash」——回测结果记的 `risk_rules_hash` 才是有意义的内容锚点。
  - 审批两步在 API 上会留下「approved 但未 active」的中间态，而中间态对 runtime 毫无意义（它只认 active），却要多一条状态迁移规则和一个失败回滚路径。合成一步后，状态机仍是 `draft → approved → active`，只是同一次写入内完成，且 DDL 的 `CHECK ((status IN ('approved','active','deprecated')) = (approved_at IS NOT NULL))` 恒成立。
  - 双指针把「编辑」与「生效」解耦：新草稿只动 `head_revision`，`active_revision` 保持不动，runtime 在审批前拿到的仍是当前生效版本；审批通过才原子地挪 `active_revision`。
- **代价 / 后果**：
  - hash 不含 description 意味着「只改说明」不产生新版本——这是**有意**的，说明文案不是规则语义。
  - 一次 approve 内要写两条 revision（旧 active → deprecated、新 → active）+ 两条审计，**必须在一个事务里**。当前 Memory Store 用进程内互斥锁近似；接 PG 后锁要换成事务，否则并发 approve 会丢更新（登记为 QT-42 未落项）。
  - 定义级 `status` 不能表示「这条规则本身被下架」——下架语义留给 revision 的 `deprecated` 与后续的删除/归档口径，不在本切片引入第四种值。
- **替代关系**：不替代 0001（两层结构不变）。本条只补 0001 之下的版本与审批语义。
