# 0004 · 监控三端点是聚合与报送，不是检测

- **状态**：已裁决（2026-10-24，QT-42 监控 3 端点开工时钉住；U7 归属裁决的落地形状）
- **场景**：U7 把 compliance / alert 归为「拆分」——6 个检测器 + 减持 + 大额报送**留 core 进程内 `alertLoop`**，
  告警的**通道编排与报送**归本仓。`ARCHITECTURE.md` §9.4 原先把 `POST /monitor/evaluate` 写成「手动触发检测
  （compliance 六检测器 + 减持 + 大额）」，这与 U7 直接冲突：本仓既没有订单 / 持仓输入，也不允许远程触发逐笔裁决。
  同时，`risk_events` 已经能写、但读侧没有口径，敞口 / 告警没有数据来源。
- **决策**：
  1. **唯一数据源 = `risk.risk_events`**。三个端点都不读订单 / 持仓 / 交易所，不 join 别人的表；
     响应里固定 `source:"risk.risk_events"`，让调用方一眼看到口径。
  2. **告警是事件的一种投影**：detector 在 core 产出告警后，按 `POST /events` 回传，`verdict` 填 `"alert"`，
     `payload` 带 `rule` / `severity` / `message`（可选 `id` / `value` / `threshold` / `attributes`）。
     本仓只做投影、排序、过滤与汇总。
  3. **`exposure` 用事件 payload 的 `notional`（或 `qty × price`）+ `side` 聚合**；字段缺失计入
     `unpriced_events`，**不补零**；超过 5000 条事件直接 400（截断的敞口会低报风险，不能当报表看）。
  4. **`evaluate` 不运行检测器、不写库**：它只按 `min_severity` / `rule` / 窗口对已回传的告警做一次报表评估，
     响应里显式写 `detection:"outside_process"`。可安全重试；汇总不允许建立在截断数据上（超限 400）。
  5. **监控端点强制鉴权闸**：`Authorizer` 未装配 → `503 auth_unavailable`，凭证缺失 → `401`，角色不足 → `403`。
     未装配时**拒绝而非放行**；其余端点仍按 QT-50 ④ 的统一面推进，不在本单扩大。
- **理由**：
  - 检测器留 core 是 U7 与「逐 bar / 逐笔裁决不出进程」的直接结论；把检测器搬进本仓等于再造一份订单输入，
    并让告警与裁决看到不同的世界。
  - 选 `risk_events` 单源而不是「再读持仓」：本仓不持有持仓真相（`db-schema.md` §2），多读一份就多一个漂移点。
  - 选「超限拒绝」而不是分页截断：敞口和汇总都是风险数字，少算比慢更危险；告警列表则允许显式 `truncated`。
  - 选可插拔 `Authorizer` 而不是自建 token：鉴权契约归 QT-50 ④，本仓只提供 fail-closed 的闸口。
- **代价 / 后果**：
  - **今天线上三端点恒 503**：QT-50 ④ 的 Authorizer 实现未接，这是有意的 fail-closed，不是故障。
  - core 的 `alertLoop` 尚未把告警投到 `POST /events`；在接线前 `alerts` / `evaluate` 只会看到空集。
  - 敞口依赖生产者把 `notional` / `qty` / `price` / `side` 放进 payload；漏字段会显示为 `unpriced_events`
    （显性缺口的代价，优于隐式补零）。
  - 外部推送通道（webhook / 消息平台）不在本切片；本仓今天的「报送」是 HTTP 报表。
- **替代关系**：不替代 0001 / 0002 / 0003；纠正 `ARCHITECTURE.md` §9.4 对 `evaluate` 的旧描述。
